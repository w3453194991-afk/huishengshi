# 冠英刹车片：选型知识库 + 线索中台

**方案说明 · v1.0 · 2026-11**

> 把「车型 / 车桥 / 旧件编码」翻译成**型号 + 依据 + 报价 + 资料包**；把「评论、私信、询盘」接住并分清谁是终端。
> 交付物是一个零安装、可离线运行的 Web 应用，外加一份标准 SQLite 库和 Excel 导入模板。

## 1. 赛题痛点，逐条回应

| 赛题里的话 | 本方案的做法 | 在系统里的位置 |
|---|---|---|
| 没有主机厂 OE 编码，OE 号打不通 | 建「编码」独立表：同一型号挂 WVA 号、工厂码、OE 号、客户叫法，613 条编码统一归一化检索 | 产品库 / 编码对照 |
| 后市场车桥常更换，光有车型锁定不了刹车片 | 不做「车型→型号」的唯一映射，改做**车型 → 车桥 → 型号**矩阵，识别到车型先给桥型表 | 智能选型 / 适配图谱 |
| 同款产品，不同主机厂编码不同 | 型号是主键，编码是外键，一个型号 N 个编码、一个编码只指一个型号 | 数据层 |
| 日均 10 条询盘、每条报价 2 小时 | 选型 10 秒 + 阶梯价自动算 + 报价单/资料包一键生成 | 智能选型 → 报价单 → 资料包 |
| 销售现场答不上「我这车用哪个刹车片」 | 三步定位法（问桥 → 拍照 → 数孔）+ 候选集 + 消歧问题 + 聊天浮窗提醒 | 智能选型 / 聊天雷达 |
| 海关数据满屏贸易公司 | 线索评分规则显式可解释，含「贸易商特征扣分」与止损线 | 询盘线索 |
| 社媒线索不准、评论私信因时差刷屏被淹没 | 按客户当地时间排序 + 关注/粉丝关系网 + 聊天消息命中车型即浮窗提醒 | 工作台 / 用户画像 / 聊天雷达 |

├──────────────────────────────────────────────────────────────┤

├──────────────────────────────────────────────────────────────┤

## 3. 三个关键设计决策

### 3.1 不做「唯一答案」，做「候选集 + 消歧问题 + 置信度」

这是整个方案最核心的一条。以本库的一汽解放 J6P 为例：同一台车，后桥可能是 457 / 485 / 498，对应的刹车片互不通用。

```
J6P  →  457 桥  →  CA9T R   （高置信，来源：官网目录）
     →  485 桥  →  CA9T R-2 （中置信）
     →  498 桥  →  CA9T R-3 （中置信）
```

所以系统识别到「J6P 后片」时，给出的是：

1. **一张桥型对应表**（销售照着念就行）；
2. **三个候选型号**，每个都带证据链（命中车型 / 命中车桥 / 命中编码 / 文本相似）；
3. **一句能直接问出口的话**：「后桥是 457 还是 485？数一下旧片孔数，8 孔还是 15 孔？」

置信度是显式打分的，不是黑箱：

```
编码精确命中            → 98
编码包含命中（长编码优先）→ 92
车型命中                → 70 + 适配置信度（已确认 20 / 高 14 / 中 8 / 低 4）
车桥命中                → 62 + 同上
文本回退                → 55 → 42
多条证据叠加，上限 100
```

对外话术也据此分级：**≥90 可直接报价 / ≥75 高置信可报但注明「以旧件为准」/ ≥58 必须先消歧**。

### 3.2 编码归一：型号是主键，编码是外键

同款产品在不同主机厂、不同国家、不同客户嘴里有完全不同的叫法：`29087`、`WVA 29087`、`BPW 05.091.46.17.0`、`KOOYING 29087`。

数据层把「型号」和「编码」拆成两张表：

```
products (272)                 codes (613)
  id  ────────────────┐          id
  code  29087         └───────── pid → products.id
  name_zh 盘式刹车片…            code  29087 / WVA 29087 / BPW05.091…
  dim   210×190×18.5            norm  29087（去空格、大写、去符号）
  material SM                   type  内部码 / WVA / 工厂码 / OE / 客户叫法
  price 6.51                    conf  高 / 中 / 低
```

检索时先归一化再匹配：精确 → 包含（长编码优先）→ 编辑距离 ≤1（仅长度 ≥5 的数字码，防误伤）。这样客户发来一个裸编码，命中率远高于「按名称搜」。

### 3.3 「发资料」不是翻文件夹，是生成

销售真正的耗时不在报价，在**凑资料**：找图片、找规格、找试验报告、拼 PDF、改客户名。

系统把这件事变成一次生成：封面（客户名 + 编号 + 型号清单 + 免责说明）→ 报价单（条款 + 阶梯价 + 运费）→ 每个型号一页数据页（图片、规格、材质、编码对照、适配、试验摘要）→ 发货前确认页（把「同车型不同桥」的风险前置到发货前）。

输出两条路径：

- **打印 → 另存为 PDF**：带产品图，适合邮件正式报价；
- **ZIP 包**：README + 报价单.html + 产品数据页.html + 3 张 CSV，体积小，适合 WhatsApp / 微信直接发。

### 3.4 数据要能自我纠错

每条适配关系都有 `置信度 + 来源 + 消歧问题`。销售在「适配图谱」里新增的关系不会直接生效，而是进入**待复核队列**；研发确认后才变「已确认」，下次匹配的置信度自动提高。

这条闭环决定了这个库三个月后是「越用越准」还是「越用越乱」。

## 4. 四个模块的具体实现

### 4.1 数据库：型号、名称、常用车型整合在一张主表

产品主表 25 个字段，其中与「认片」直接相关的：

| 字段 | 说明 | 当前覆盖 |
|---|---|---|
| `code` | 冠英型号（唯一） | 272 |
| `name_zh` | 中文名，规则：`品类 + 型号（首个适配车型）`，如「鼓式衬片 HOWO1（重汽豪沃）」 | 272 |
| `name_en` | 官网英文名（保留原样，便于对外） | 272 |
| `apps` | 从官网标题推断的适配对象（BPW / Actros / HOWO…） | 122 |
| `common_vehicles` | 来自适配关系的具体车型 | 44 条关系覆盖 26 车型 |
| `dim` / `holes` | 规格与孔数（现场最快判据） | 缺口最大，优先补 |
| `material` | NAO / SM / LM / CM / HD / WT，带 μ 与温度区间 | 100% |

同一份数据落在三个地方，口径完全一致：

- `assets/data.js` —— 前端离线快照（`window.DB`）
- `data/db.json` —— 给 IT / BI 的 JSON
- `data/guanying.db` —— SQLite，11 张表 + 2 个视图 + 索引，可直接 `SELECT`

```sql
-- 客户发来一个编码，问「这是什么、多少钱、装什么车」
SELECT * FROM v_code_lookup WHERE matched_code = '29087';

-- 某车型所有桥型对应
SELECT vehicle, axle, pos, model, conf FROM v_product_fitment
WHERE vehicle LIKE '%J6P%';
```

### 4.2 用户画像与关系网

目标不是「做个粉丝列表」，而是回答销售的两个问题：**谁值得花时间**、**谁能替我们说一句话**。

数据模型（17 个演示账号，接平台 API 后可批量导入）：

| 字段 | 用途 |
|---|---|
| `type` | 车队 / 修理厂 / 配件店 / 经销商 / 司机 KOL / 采购经理 / 贸易商 |
| `followers` / `following` | 影响力与「他关注谁」 |
| `tags` | 常出镜/常提的车型，直接映射到可推型号 |
| `intent` | 意向度（0–100），决定跟进优先级 |
| `community` | 拉美 / 中东 / 东南亚 / 非洲 / 欧亚，用于分区运营 |
| `action` | 系统给出的下一步动作，不是空话 |

关系网用 SVG 画：节点大小=粉丝量，颜色=区域，外圈=高意向（≥85），橙色虚线=关注品牌号。点节点出画像卡：粉丝/关注/作品/互动率、画像标签、关系网名单、**提到车型 → 可推型号 → 报价**、推荐动作、一键生成该语种私信草稿。

三个立刻能用的判断：

1. **关键节点**：粉丝里同时出现多个区域账号的，是跨区影响者，优先寄样。
2. **终端 vs 中间商**：`@mekongparts`（贸易商，意向 34）只发目录；`@jorge.ramirez`（采购经理，意向 91）直接约会议。
3. **内容反哺**：谁经常拍哪个车型，就给他对应的型号和脚本，转化率最高。

### 4.3 聊天浮窗：后台听消息，命中车型就提醒

销售的真实场景是：WhatsApp、TikTok 私信、Facebook、Instagram 四个窗口同时闪，时差一乱就漏。

浮窗做三件事：

1. **聚合**：四个通道的消息进同一条流，标来源、标当地时间；
2. **识别**：每条消息过一遍匹配引擎（阿语、西语、葡语、印尼语、越南语都能识别车型/车桥/编码，靠的是别名表而不是翻译）；
3. **提醒**：命中就弹卡片 —— `客户问 Actros → 29162 · $x/套 · 210×190×18.5`，附「加入报价」「复制回复」；没命中就自动给「三步定位法」索要照片的话术。

识别链路和选型页是同一条，所以口径不会打架。当前为**演示回放模式**（10 条多语种真实风格消息），接入方式见 §6。

### 4.4 获客内容引擎：泛流量做认知，垂直流量做转化

刹车片是低关注度品类，纯硬广没人看。方案把内容分两条线：

| 流量类型 | 内容形态 | 目标 | 衡量 |
|---|---|---|---|
| 泛流量 | 「为什么你的车 3 个月吃一副片」「同车型三种桥」这类反常识科普 | 让司机/修理厂记住 KOOYING | 完播率、评论里问型号的数量 |
| 垂直流量 | 具体型号拆箱、断面、装车、台架数据 | 让采购能直接下单 | 私信询盘数、资料包索取数 |

**热门视频雷达**：按语种/国家列出近 7 天高互动选题（12 条演示数据），每条标注「为什么火」的角度（同车型不同桥、每万公里成本、原厂 vs 副厂、没有编码怎么认片…）和可挂的型号。

**脚本生成器**：选产品 + 市场 + 语种 + 平台 + 时长 + 痛点，输出

- 6 个分镜（0–3s 钩子 / 3–8s 冲突 / 8–16s 产品特写+卷尺 / 16–24s 试验背书 / 24–30s 装车 + CTA）
- 目标语种口播稿（ES / PT / AR / EN / ID / VI / TR）
- 话题标签、拍摄清单
- **一段可直接粘贴给任意大模型的提示词**（含产品参数、痛点、平台、时长、合规要求）

最后这项是关键：本机生成的是「结构正确的初稿」，真正的母语润色交给大模型或本地员工，避免编造认证、避免机翻腔。

## 5. 五分钟演示脚本

1. **痛点**：顶部搜「豪沃A7 后片 200 套」→ 出型号 HOWO1（86 分）+ 依据链 + 桥型表 + 3 个消歧问题。
2. **报不上价的场景**：搜「解放J6P 后片」→ 不急着给型号，先给 457/485/498 三行桥型表。
3. **客户只给编码**：搜「58144-45211」→ 98 分直接命中，附编码类型与来源。
4. **凑资料**：加入报价 → 报价单（阶梯价 200 套自动落到 0.94 档）→ 资料包 → 打印预览 → 另存 PDF / 下载 ZIP。
5. **接线索**：工作台看到「现在该联系谁」，按当地时间排好；进询盘线索看评分依据。
6. **浮窗**：点右下「模拟新消息」→ 阿语询盘 → 1 秒内弹出「Actros → 29162」。
7. **画像**：用户画像页点 `@jorge.ramirez` → 意向 91、480 台车队 → 生成西语私信。
8. **内容**：获客内容页点「用此选题」→ 自动带出该市场语种和型号 → 生成脚本 → 复制 AI 提示词。

## 6. 落地路线

| 阶段 | 时间 | 做什么 | 产出 |
|---|---|---|---|
| 一期 | 2 周 | 用真实价格表/尺寸表替换演示数据；研发复核 44 条适配；给 10 个外贸配浏览器书签 | 可对外的选型与报价 |
| 二期 | 30 天 | `guanying.db` 放公司内网，做多用户版（登录、权限、审计）；接孚盟 CRM 客户与订单 | 团队共用一套库 |
| 三期 | 60 天 | 接 WhatsApp Business API / TikTok 私信 webhook，聊天浮窗转实时；接平台数据做画像 | 线索不漏 |
| 四期 | 90 天 | 内容排期与素材库；大模型 API 做母语脚本与自动回复草稿；按询盘-报价-成交做归因 | 获客可衡量 |

**集成方式**：SQLite 可原地被 BI 工具读取；若要多用户，迁到 MySQL/PostgreSQL 只改连接串（表结构已按三范式设计，无 JSON 依赖，`apps/common_vehicles` 两列为兼容旧系统保留 JSON 文本）。

**不建议做的事**（写在方案里，避免走弯路）：

- 不要试图一次把「所有车型×所有桥」补全 —— 先补近 12 个月实际成交的 50 个型号；
- 不要让销售自由编辑型号主数据 —— 只能提「待复核」，否则编码体系三个月就烂；
- 不要用爬虫抓私信 —— 违反平台条款，用官方 API 或人工转发。

## 7. 边界与风险（必须如实告知）

1. **演示数据**：价格、MOQ、交期、客户名、试验报告编号均为示例结构，不代表公司真实数据。上线前必须替换。
2. **适配置信度**：当前 44 条适配中，0 条「已确认」、16 条「高」、23 条「中」、5 条「低」。**低置信度不得直接对外报价**，界面已用颜色区分。
3. **画像与视频数据**：17 个账号、12 条视频为演示结构，用于验证交互与指标；真实数据需通过平台官方接口或人工录入。
4. **聊天浮窗**：当前是本地回放演示，不连接任何真实账号；接入需企业号 + 官方 API 授权。
5. **隐私**：客户表只存公司名、国家、联系人称谓与公开联系方式，不存身份证、银行卡、私人手机号；导出功能面向内部，建议加登录。
6. **认证表述**：脚本生成器内置约束「不夸大认证」，对外只写实际持有的 IATF 16949 / ECE R90 覆盖范围。

## 8. 附录

### 8.1 定价公式

```
单价 = 基准价 × 材质系数 × 数量阶梯 × 客户等级 × 价格等级
数量阶梯：1–99 → 1.00 ｜ 100–299 → 0.94 ｜ 300–999 → 0.88 ｜ ≥1000 → 0.82
客户等级：A → 0.97 ｜ B → 1.00 ｜ C → 1.03
价格等级：大客户 → 0.95 ｜ 标准 → 1.00 ｜ 经济 → 0.96
材质系数：NAO 1.00 ｜ SM 1.04 ｜ LM 1.08 ｜ CM 1.12 ｜ HD 1.18 ｜ WT 1.35
```

运费为估算值（按 CBM 与重量取大者 × 线路单价），正式报价以货代为准确认。

### 8.2 线索评分

| 维度 | 权重 | 说明 |
|---|---|---|
| 基础分 | 30 | 有明确需求即得 |
| 终端特征 | +18 | 车队/修理厂/运输公司/物流 |
| 贸易商特征 | −14 | Trading / Import & Export / FZE |
| 车型或编码明确 | +10 | 能直接匹配到型号 |
| 数量明确 | +12 | 出现 sets / 套 / pcs / 片 |
| 联系方式完整 | +10 | 有联系人而非仅公司名 |
| 时区可判 | +4 | 能算工作时间 |

≥75 优先跟进 ｜ 55–74 正常跟进 ｜ <55 只发目录。
